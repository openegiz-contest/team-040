## Задача

Диспетчер смены сравнивает варианты остановки участка и вывода персонала при признаках нестабильности выработок. Двойник связывает состояние выработок, показания датчиков, людей, работу участка и доступность выходов.

Объект условный, данные синтетические. Типологические и числовые ориентиры должны быть явно отделены от допущений модели. Наименование реального предприятия не означает, что воспроизведены его геометрия или условия эксплуатации.

## Демонстрация результата

1. На пространственной схеме видны выработки, выходы, участки работ, датчики и условные работники. Выбор объекта открывает его состояние из Ditto и время обновления.
2. Сценарий изменяет состояние участка; изменения наблюдаются в телеметрии и связанных двойниках.
3. На сохранённом состоянии принятия решения симулятор рассчитывает прогноз вариантов; диспетчер сравнивает их и запускает выбранный вариант. На схеме изменяются доступные проходы, работа участка и движение людей.
4. Отдельное сравнение завершённых прогонов показывает время выхода всех (если вышли все), число работников на опасном участке, человеко-секунды воздействия, число работников без доступного маршрута и суммарный простой участков. Прогноз и факт разделены. Это результаты симуляции, а не доказанный эффект на реальном предприятии.
5. Для повторной проверки доступны отмена условия сценария и отдельный сброс к исходному состоянию. Отмена условия сама по себе не возвращает людей на прежние позиции и не стирает историю.

## Объём первой версии

| Часть | Содержание | Проверяемый результат |
|---|---|---|
| Пространственная модель | Собственная сеть связанных выработок, развилки, рабочие участки и выходы | Визуализация и расчёт маршрутов используют одну топологию |
| Геомеханическое состояние | Синтетические деформации, их тренд и сейсмические события; объяснение срабатывания | У состояния есть наблюдаемые причины, единицы измерения и источник/допущение каждого параметра |
| Персонал и работа участка | Условные работники, положения, перемещение, состояния участка | Люди не проходят через закрытые связи; остановка участка меняет производственный процесс |
| Действия диспетчера | Остановка участка, вывод персонала, сравнение вариантов | Результат меняется в модели и затем в данных платформы |
| Качество данных | Время последнего измерения, потеря связи, недостоверность данных | Потеря датчика не превращается в нормальное состояние участка |
| Визуализация | Лёгкая пространственная схема, выбор объектов, легенда, события и сравнение прогонов | Причинная цепочка видна без чтения кода и работает без GPU |

Предлагаемые сценарии первой версии:

- Нарастание признаков нестабильности в одном участке: изменение наблюдаемых величин → состояние участка → решение диспетчера → последствия для работы и людей.
- Перекрытие прохода: изменение доступности связи → перерасчёт маршрутов → обход или явное отсутствие пути. Сценарий задаёт происшествие; модель не заявляет, что физически предсказала разрушение породы.
- Потеря датчика или связи: устаревание данных → неопределённость состояния → отображение ограничения для принятия решения.

Для сравнения действий нужны одинаковое исходное состояние, одинаковые внешние события и одинаковый seed. Нельзя сравнивать разные случайные аварии и приписывать разницу алгоритму.

Сравнимость подтверждается comparison_key, включающим состояние в момент решения, версии модели и параметров, расписание событий, горизонт и состав людей. Один seed недостаточен. Ручные изменения условий могут сделать прогон несравнимым.

## Интеграция с OpenEgiz

```text
Симулятор и обработка команд
          |
          v
         MQTT --> Eclipse Ditto --> API чтения платформы --> Интерфейс
                       |
                       v
                история платформы
```

- Выработки, участки, датчики, работники и состояние смены представлены двойниками.
- Связи хранятся явно: расположение, принадлежность участку, соединение выработок, контроль датчиком.
- Геометрия и манифест объектов лежат в атрибутах Ditto; UI и симулятор используют один источник топологии.
- UI получает производственные состояния из платформы; прямой поток симулятор → UI не заменяет MQTT → Ditto.
- UI читает согласованную проекцию сцены внутри shift; отдельные двойники сохраняются. Публикация shift последним не объявляется транзакцией между объектами.
- Различаются время измерения, шаг модели и настенный heartbeat публикации. На паузе heartbeat продолжается.
- Команда идёт live-сообщением в shift, имеет идентификатор и подтверждение в состоянии. HTTP 202 не означает исполнения; повторная отправка не должна дублировать происшествие.
- UI доступен через серверный прокси на 127.0.0.1:8088; пароль Ditto не передаётся в код страницы.
- Статические ресурсы интерфейса поставляются с решением; ключи внешних сервисов не требуются.

## Что проверять

- Геометрические длины, скорость движения, шаг времени и время прибытия согласованы в одних единицах.
- Число работников сохраняется; один работник не находится одновременно в нескольких участках.
- Закрытый или признанный недоступным проход исключён из маршрута; при отсутствии пути система это явно показывает.
- Устаревшие показания не окрашивают участок как нормальный. Возврат данных и отмена события обрабатываются раздельно.
- Одинаковые входы дают одинаковый прогон; разница сравниваемых вариантов вызвана действиями диспетчера.
- При потере платформы UI показывает недоступность данных, а не продолжает выдавать локальную анимацию за актуальные двойники.
- После сброса сценарий можно воспроизвести; команды, применённые повторно, не искажают состояние.
- Чистый старт, повторный старт и запуск всех описанных сценариев проходят по README без ручной правки файлов.

## Ограничения и приоритеты

Синтетический индекс состояния не является вероятностью обрушения. На синтетических данных нельзя подтвердить точность прогнозирования реального обрушения или пригодность маршрута для реальной эвакуации. Пороговые значения модели требуют обоснования и не выдаются за нормативы или производственные уставки.

В первую версию не входят полная геомеханическая FEM-модель, предсказание точного времени обрушения, промышленное управление оборудованием, подробная вентиляционная модель и чат-ассистент. Расширение допустимо после проверяемого основного сценария.

Уникальность в Казахстане не подтверждена. Сравнивать следует конкретные возможности с публично описанными решениями; отсутствие функции в публичной статье не доказывает её отсутствие на предприятии.
