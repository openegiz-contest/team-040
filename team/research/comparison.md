# Сравнение трёх действий в четырёх сценариях

Расчёт 14 октября 2026 года, модель 0.1, топология t1. Собственная синтетическая
шахта: 6 работников, два участка, скорость 1,25 м/с. Это 12 автономных исполнений
модели, а не 12 проверок стенда MQTT/Ditto и не эксперимент на действующей шахте.
Числа и ограничения: [реестр параметров](parameters.md).

## Как воспроизвести

Из корня репозитория (на Windows заменить python3 на py -3):

```sh
python3 -m team.sim.comparison --output team/research/comparison.json
python3 -m team.sim.comparison --check team/research/comparison.json
python3 -m unittest team.sim.test_comparison -v
```

Первая команда сохраняет JSON и печатает таблицу. Вторая повторяет эксперимент
и сравнивает весь результат с сохранённым. Модель, параметры и checkpoint-хэши
включены в [comparison.json](comparison.json). Для интерфейса доступны причины,
область действия, пути до/после события, прогнозы, факт, состояния каждого
работника и участка. Формат — отчёт для анализа, не новый API или замена Ditto.

Для каждого сценария модель доходит до первой точки решения. Все три исполнения
начинаются с отдельных полных копий этого состояния: одинаковые люди, измерения,
ограничения, расписание событий и comparison_key. Каждое действие выполняется
900 секунд после решения; исходная точка остаётся неизменной. Ручных изменений
условий в ходе исполнения нет. Между разными сценариями ключи различаются.

Проверены точное совпадение метрик факта с соответствующим прогнозом и завершение
горизонтом. Прогноз и факт используют один расчётный код: совпадение подтверждает
согласованность реализации, но не физическую точность модели.

## Таблица результатов

«Вывести затронутые участки» — действие stop_withdraw_zone. Область задаётся
incident.scope; это не всегда один участок. Ниже объяснены два случая, когда
оно фактически выводит всех. «—» означает, что все шестеро не вышли за окно;
числовое время выхода всех отсутствует, а не равно нулю.

|---|---|---:|---:|---:|---:|---:|---:|
| Нестабильность | Наблюдать | 0 | — | 0 | 2700 | 0 | 0 |
| Нестабильность | Вывести затронутые участки | 3 | — | 0 | 96 | 0 | 900 |
| Нестабильность | Вывести всех | 6 | 850 | 0 | 96 | 0 | 1800 |
| Закрыт основной проход | Наблюдать | 0 | — | 0 | 0 | 0 | 0 |
| Закрыт основной проход | Вывести затронутые участки | 6 | 850 | 0 | 0 | 0 | 1800 |
| Закрыт основной проход | Вывести всех | 6 | 850 | 0 | 0 | 0 | 1800 |
| Закрыт выход с участка | Наблюдать | 0 | — | 3 | 0 | 0 | 0 |
| Закрыт выход с участка | Вывести затронутые участки | 3 | — | 3 | 0 | 0 | 1800 |
| Закрыт выход с участка | Вывести всех | 3 | — | 3 | 0 | 0 | 1800 |
| Потерян датчик | Наблюдать | 0 | — | 0 | 0 | 2700 | 0 |
| Потерян датчик | Вывести затронутые участки | 3 | — | 0 | 0 | 96 | 900 |
| Потерян датчик | Вывести всех | 6 | 850 | 0 | 0 | 96 | 1800 |

**Единицы и границы:** воздействие опасности — сумма времени людей в зоне danger
после решения; 3 человека × 900 с = 2700 чел·с. Неопределённость считается отдельно:
нахождение в контролируемой зоне с unknown или неизвестная достижимость согласно
metrics(). Проходы без датчиков не входят автоматически в этот показатель:
нулевая величина не означает, что вся шахта наблюдается датчиками.
Простой суммируется по участкам после решения: 900 участок·с = один участок
остановлен на 15 минут; 1800 = два участка по 15 минут, а не 30 минут прогона.
Возобновление работы после вывода в этих действиях не предусмотрено.

## Почему результаты различаются

**Нестабильность (p-instability).** На 60-й секунде зона A получает синтетический
сигнал 2,6 мм/ч при условном пороге 2 мм/ч. Наблюдение оставляет троих в danger
на всё окно: 2700 чел·с. При выводе они покидают опасную выработку через 16, 32 и
48 секунд: 96 чел·с суммарно. До поверхности группа A доходит полностью за
546 секунд. Группа B при локальном действии продолжает работать: 3/6 вышедших
означает выполненный приказ по A, но не полный вывод смены.
Вывод всех не уменьшает воздействие на A дополнительно, зато выводит ещё троих
из B и удваивает простой. Последний человек из B выходит через 850 секунд.
Это выбор между разным охватом и простоем в заданной модели, а не универсальная
рекомендация оставлять второй участок работать при реальном происшествии.

**Закрыт основной проход (p-detour).** На 60-й секунде закрывается w-04.
Путь остаётся доступным всем. Например, путь worker-a1 увеличивается с
641,886 до 664,773 м — примерно на 22,887 м (18,31 с при принятой скорости).
Путь worker-b1 не меняется. Итоговое время выхода всех остаётся 850 с, потому
что его определяет более длинный путь группы B. Одно итоговое время скрывает
локальное удлинение маршрута, поэтому в JSON сохранены пути каждой группы.

Обнаруженное ограничение: `_open_decision()` при любом закрытом проходе включает
в scope домашние участки всех оставшихся под землёй работников. Поэтому scope
содержит A и B, а локальное действие совпадает с полным выводом. Это не доказательство
одинаковой полезности двух различных стратегий: в этом случае стратегии
исполняют одинаковые распоряжения. Алгоритм определения затронутых участков
следует уточнить отдельным изменением; в этом эксперименте он не подменялся.

**Закрыт выход с участка (p-trapped).** Закрывается текущая выработка w-07 с
тремя работниками A. Они остаются на исходных позициях 20/40/60 м: модель не
переносит их через закрытую связь. Команда вывода освобождает только группу B;
трое из A остаются без маршрута, all_out=false. Оба действия вывода снова имеют
scope A+B. Они не включают разблокирование прохода или спасательные операции.
Нулевое воздействие danger здесь не означает безопасность: сценарий меняет
проходимость, а не деформационные показания. Трое без маршрута — отдельный
критический результат. Нулевой простой при observe отражает упрощённую модель
работы по укомплектованности; влияние закрытия пути на снабжение не моделируется.

**Потерян датчик (p-sensor).** Связь отключается на секунде 60, последнее
измерение имеет время 59. Порог stale=15 с достигается на секунде 74, тогда
открывается решение. Окно сравнения начинается в 74, а не в 60; задержка
обнаружения относительно события составляет 14 с. Старый нормальный сигнал
не превращается в подтверждение безопасности: состояние становится unknown.
Наблюдение даёт 2700 чел·с неопределённости. Вывод A сокращает её до 96 чел·с;
полный вывод даёт то же снижение, но охватывает B и удваивает простой.
Прогноз имеет forecast_quality=partial. Это отсутствие данных, не установленная
опасность и не нулевой риск; в таблице эти показатели разведены.

## Вывод для демонстрации

Система уже позволяет показать различие между выводом конкретного участка и
всей смены, между потерей пути и удлинением пути, между опасным показанием и
отсутствием знания. Автоматического «лучшего варианта» в отчёте нет: полный вывод,
охват приказа, воздействие, неизвестность и простой — разные критерии.

Перед следующей конкурсной демонстрацией приоритетно уточнить scope при
перекрытии проходов и явно показать в интерфейсе, какие участки получат приказ.
После изменения модели нужно заново сгенерировать отчёт и проверить прогноз/факт.
