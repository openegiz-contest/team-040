# Расчётная модель рудника

Это собственная модель команды, написанная по Concept в SUBMISSION.md. Режим
`python -m team.sim` выполняет автономный эксперимент. Сервис
`python -m team.sim.service` создаёт метаданные в Ditto и передаёт динамическое
состояние через MQTT. Проверка Python сама по себе не подтверждает работу всей
цепочки MQTT → Ditto → интерфейс; для неё есть `python -m team.smoke`.

## Запуск из корня репозитория

Зависимости: стандартная библиотека Python 3.11+. На Windows вместо `python3`
используйте `py -3`.

```sh
python3 -m unittest team.sim.test_model -v
python3 -m team.sim --preset p-instability --option withdraw_all
python3 -m team.sim --preset p-trapped --option withdraw_all --export /tmp/mine-result.json
```

Пресеты: `p-instability`, `p-detour`, `p-trapped`, `p-sensor`. Варианты: `observe`,
`stop_withdraw_zone`, `withdraw_all`. Результат содержит три прогноза и фактическое
исполнение выбранного варианта тем же кодом. Ничего не отправляется по сети.
Экспорт не содержит выдуманных `_modified` и `_revision`: эти метаданные должна
присвоить платформа. Такой файл нельзя выдавать за полученный из работающей Ditto.

## Что реализовано

- Одна топология для графа маршрутов и атрибутов визуализации: два подземных
  горизонта, 12 выработок, два выхода, два участка, два датчика, шесть работников.
- Расстояние — сумма длин сегментов ломаной. Работник проходит заданное расстояние
  за секунду, включая переход между выработками, и выходит только на конце пути.
- Закрытая текущая выработка останавливает человека на месте. После открытия он
  продолжает движение. Опасную/неизвестную контролируемую выработку можно покинуть,
  но нельзя включить в маршрут как новый промежуточный участок.
- Датчик сохраняет последнее измерение при отключении. Его возраст отсчитывается
  по модельному времени; потеря данных не снимает известное опасное ограничение.
- Первый инцидент приостанавливает время для выбора. Прогнозы считают три копии
  полного состояния на одном горизонте. На паузе сохраняется публикация heartbeat.
- В текущей реализации один исполняемый вариант на прогон. Изменение условий после
  выбора сохраняет исходный прогноз и помечает факт `comparable=false`. Новое
  сравнение начинается новым прогоном. Плановые события продолжают исполняться.
- В конце горизонта модель останавливается, архивирует факт с `completion_reason=horizon`.
  Досрочный reset архивирует причину `reset`, не объявляя успешную эвакуацию.
- Подтверждения команд и полный журнал дедупликации переживают reset и рестарт
  через `Store`. Окно последних 32 подтверждений независимо от полного журнала.
  Владелец состояния должен быть один; конкурентный доступ нескольких процессов
  к одному checkpoint не поддерживается. Файл сохраняется через fsync и замену;
  гарантия при потере питания файловой системы отдельно не проверялась.
- `twins.snapshot` создаёт согласованный `shift.scene` и отдельные двойники.
  `mqtt_messages` строит modify `/features`, shift последним. Это не межобъектная
  транзакция. Публиковать нужно результат транзакции Store, после сохранения seq.

## Допущения и пределы

Все числа в `topology.py` — **настройки синтетической демонстрации**, пока не
калиброванные по промышленным измерениям. Геометрия не воспроизводит реальный
рудник. Скорость 1,25 м/с одинакова для каждого ребра; уклон, усталость, очереди,
пропускная способность, время оповещения и транспорт не моделируются. Выходы —
условные пешие пути, не шахтные подъёмники. Их длины считаются по геометрии.

Скорости смещения 0,2/2,6 мм/ч, пороги 1/2 мм/ч, stale/lost 15/30 секунд,
производительность 30 т/ч на участок, три работника для работы и горизонт 900 с
выбраны для демонстрации. Рост показания при условии нестабильности задаётся
сценарием. Индекс — отношение скорости к условному порогу с ограничением 0–1,
**не вероятность обрушения**. Реальная устойчивость массива не рассчитывается.

На участке пока один синтетический экстензометр. Геофоны, сейсмика, резервирование
датчиков, деградация позиционирования и изменение доступности выхода командами
не реализованы. У транспортных выработок без датчиков `hazard_state=unknown`,
`data_quality=none`; их проходимость — явное допущение. Производство пока только
текущая скорость и простой, без баланса руды и оборудования.

Воздействие считается по состоянию в начале каждого секундного интервала.
`last_out_s` округлён вверх до шага 1 с и отсутствует при неполном выходе общей
группы. `downtime_s` имеет единицу zone*s и включает простой до решения;
воздействие вариантов отсчитывается от контрольной точки решения.

Сервис, bootstrap, прокси и экспорт истории подключаются через `team/compose.yml`.
Команда `make up` загружает этот overlay автоматически. Пароль Ditto читается из
окружения; состояние и журнал команд лежат в Docker volume `team040-state`.
Подписка команд QoS 1 с постоянным MQTT client id подтверждается после сохранения
состояния на диск. HTTP bootstrap не записывает динамические признаки: они идут
только через MQTT. `publication_seq` сохраняется до публикации.

История читает только `opentwins/twin/events/#`. Экспортирует скалярные значения
признаков; scene, route, commands и другие структуры остаются в Ditto и не
разворачиваются в метрики. Счётчики хранятся целыми, физические величины и
длительности — float, чтобы нулевое начальное измерение не меняло тип ряда.

Журнал содержит команды и условия; отдельные события смены
маршрутов/опасности ещё необходимо добавить. Удлинение относительно базового
маршрута пока не публикуется. Эти ограничения нельзя скрывать в SUBMISSION.md.
