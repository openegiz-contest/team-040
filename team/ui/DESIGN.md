## 1. Пробелы и противоречия текущего плана

**1.1. «Сравнить варианты» не определено во времени.** В [SUBMISSION.md](../../SUBMISSION.md) (строка 13) и в [team/PLAN.md](../PLAN.md) (строка 15) диспетчер сначала сравнивает варианты, затем запускает один. Строки 16 и 36 плана описывают другое: сравнение уже завершённых прогонов с одинаковым исходным состоянием, событиями и seed. На одном работающем стенде нельзя провести три вывода персонала и после этого выбрать один. Последствие: без прогноза в момент выбора на экране нечего сравнивать, и решение из замысла не поддержано. Если прогноз посчитает сам UI, появятся данные не из платформы (Правила, пункт 6.2) и второй расчёт маршрутов. Отдельно: условие, заданное кнопкой вручную, попадает в разные прогоны в разный модельный момент, и требование строки 36 об одинаковых внешних событиях не выполняется само собой.
**Предложение.** Сторона симуляции публикует для текущего состояния детерминированный прогноз по каждому варианту (время до выхода последнего работника, число работников, остающихся в опасной зоне, число работников без маршрута, простой участков) как данные двойников. После исполнения рядом с прогнозом записываются фактические показатели. Завершённые прогоны сравниваются в отдельной таблице. Прогноз везде подписан «прогноз модели».

**1.2. Не выбран канал команд и владелец состояния.** [team/PLAN.md](../PLAN.md), строка 54, требует идентификатор команды и подтверждение, но не называет канал. Факты: у Mosquitto один TCP-слушатель без WebSocket (`deploy/compose/mosquitto/mosquitto.conf`, строка 4), браузер не может публиковать в MQTT; телеметрия заменяет все признаки двойника целиком (`OPENEGIZ.ru.md`, строка 114), поэтому запись UI в признак чужого двойника стирается следующим тиком; live-сообщения Ditto пересылаются в MQTT (`deploy/compose/init/mosquitto-target-connection.json`, строки 10–15), но без подтверждения, и попадают в Telegraf, подписанный на `opentwins/#` (`deploy/compose/telegraf/telegraf.conf`, строка 24). Последствие: состояние «команда ещё не выполнена» нельзя спроектировать, пока подтверждение не определено как состояние двойника.
**Предложение (сторона UI).** UI отправляет live-сообщение Ditto во входящие одного управляющего двойника с идентификатором `command_id`, созданным в браузере. Симулятор подтверждает только через состояние двойников: запись о команде со статусом и тиком. UI никогда не пишет признаки двойников симулятора. Повтор с тем же `command_id` идемпотентен. Альтернатива: двойник «желаемого состояния», которым владеет UI, а симулятор читает его изменения из событий двойников. Она оставляет запрос в платформе и переживает перезапуск симулятора, но делает UI вторым автором состояния и требует прав записи и правила очистки. Выбор остаётся за Codex (вопрос 1 в разделе 5.7).

**1.3. У актуальности трое часов, план называет одни.** [team/PLAN.md](../PLAN.md): строка 53 (время модели и номер шага в каждом обновлении), строка 27 (качество данных), строка 79 (устаревшие показания). Платформенная метка `_modified` — это настенное время, и её обновляет каждая полная замена `/features` (по документации Ditto, на стенде не проверено), поэтому потерянный датчик выглядит свежим. При ускорении возраст по настенным часам не равен возрасту по модели. Источник принимает телеметрию с QoS 0 (`deploy/compose/init/mosquitto-source-connection.json`, строка 11): тик может пропасть. InfluxDB отстаёт не меньше чем на 10 с (`deploy/compose/telegraf/telegraf.conf`, строки 5 и 10). Последствие: правило «устаревшие показания не окрашивают участок как нормальный» нельзя выполнить по одному `_modified`, а если состояние участка выведет UI, реализаций станет две.
**Предложение.** Каждый датчик несёт тик и модельное время своего измерения и состояние связи. Каждый двойник несёт тик, на котором рассчитан. Один управляющий двойник публикуется в тике последним и служит отметкой завершения кадра. Производные состояния, включая `unknown`, считает сторона симуляции, UI их только показывает. Пороги устаревания — параметры модели в модельных секундах. Остановку потока (нет нового тика) UI определяет по настенному возрасту, сравнивая заголовок `Date` ответа Ditto с `_modified` управляющего двойника, а не по часам браузера.

**1.4. У «одной топологии» нет места хранения.** [team/PLAN.md](../PLAN.md): строка 23 («визуализация и расчёт маршрутов используют одну топологию») и строка 51 («связи хранятся явно»). Если UI привезёт свои координаты выработок, топологий станет две. Если UI будет считать маршруты для отрисовки, появятся два расчёта, и нарисованный маршрут может не совпасть с тем, по которому идут работники.
**Предложение.** Геометрия (локальные координаты x, y, z в метрах, длины, связи) хранится в атрибутах двойников, UI рисует только из Ditto. Маршруты считает только сторона симуляции и публикует по каждому работнику. UI маршрут не вычисляет никогда. Признак `topology_version` позволяет UI заметить расхождение. Список двойников UI получает поиском Ditto, который отдаёт результаты страницами (раздел 5.4).

**1.5. Не спроектирован доступ UI к платформе и доступ жюри к сценариям.** [team/PLAN.md](../PLAN.md), строки 52 и 55. Ditto за `ditto-nginx` требует Basic-аутентификацию для `/api` и `/ws` (`deploy/compose/ditto/nginx.conf`, строки 41–72), пароль создаётся для каждой копии репозитория и лежит только в `deploy/compose/.env`; этот файл появляется при первом `make up` и в git не попадает (`scripts/compose-env.sh`, строки 49–51). Grafana требует входа (`deploy/compose/docker-compose.yml`, строки 323–324; анонимный доступ и встраивание не включены в `deploy/compose/grafana/grafana.ini`). Как жюри запускает сценарии, не опубликовано. Последствие: статическая страница не прочитает Ditto без запроса пароля или пароля, зашитого в JS, а сценарий, которому нужна команда в терминале, могут не увидеть.
**Предложение.** Контейнер UI — статический сервер и обратный прокси того же origin `/ditto/` → `http://ditto-nginx:80/`. Прокси подставляет `Authorization: Basic ${DITTO_BASIC_AUTH}` на сервере, пропускает только GET-пути чтения и один POST-путь команды, слушает `127.0.0.1` (предлагаю `TEAM_UI_PORT=8088`; порты 3000, 8080, 8085, 8086, 8090 и 1883 заняты платформой). Прокси не хранит состояние и ничего не вычисляет: UI по-прежнему получает данные из платформы. Каждое условие сценария, его отмена и сброс — подписанные кнопки на основном экране; Codex может продублировать их документированными командами. Это затрагивает overlay-файл compose и Makefile, то есть зону Codex (раздел 7).

## 2. Основной экран

### 2.1. Подход к визуализации

Схема — **аксонометрическая проекция, нарисованная в SVG**: два-три горизонта, расположенные по отметкам один над другим, соединённые стволом, наклонным съездом и запасным выходом (восстающим). Подземный рудник пространственен именно по горизонтам, и проекция показывает это без WebGL. Переключатель вида открывает план одного горизонта. На экране горизонты разнесены так, чтобы не перекрывать друг друга; вертикаль не в масштабе, и это подписано на схеме.

Основание выбора. Критерий «Визуализация рудника» (25 баллов из 100, Правила) требует пространственный объект, отображающий данные двойников, ход процессов и последствия сценариев. Машина судьи не имеет GPU: «рендеринг выполняется без графического ускорителя, поэтому объём трёхмерных сцен рекомендуется минимизировать» (Окружение судьи). SVG даёт чёткий текст, DOM, который читают тесты и ИИ-жюри, и не зависит от программного рендерера. От чего отказываемся: свободная камера, перспектива, фотореализм, произвольный поворот сцены.

Что не опубликовано Организатором и чем это закрыто:

| Не опубликовано | Мера в проекте |
|---|---|
| Браузер и его версия | Только базовая веб-платформа: ES-модули, `fetch`, SVG, CSS grid. Значки — встроенные SVG, а не символы шрифта или эмодзи. Числа и время форматирует свой код, а не локаль браузера. Время платформы показывается в UTC с подписью |
| Размер окна | Раскладка проверяется на 1280×720 и 1920×1080 без горизонтальной прокрутки |
| Нажимает ли ИИ-жюри кнопки или только смотрит | Экран без единого нажатия показывает шахту, людей, состояния, легенду и текущий сценарий. Нет сведений, доступных только при наведении. Все состояния продублированы текстом в DOM. Точные виды открываются ссылкой |
| Программный рендерер и версия WebGL | WebGL и `canvas` не используются. Нет фильтров SVG и CSS, размытия и теней |
| Целевая частота кадров | Нет постоянной анимации и мигания: любой отдельный кадр — верный снимок состояния |
| Содержание Типового Решения | Не сравниваемся с ним и не заявляем отличий; экран строится от решения диспетчера из замысла |

Остальные решения:

- **Обновление** около 1 раза в секунду опросом Ditto через прокси. Положения сглаживаются короткими CSS-переходами между двумя полученными положениями; постоянного цикла анимации нет. SSE — возможное улучшение позже.
- **Без шага сборки:** обычные ES-модули, SVG и CSS, раздаваемые nginx, без фреймворка. Причины: воспроизводимый запуск в пределах опубликованного лимита 75 минут ([team/PLAN.md](../PLAN.md), строка 72), нечего скачивать, исходный код читается как есть. Цена: нет типизации и готовых компонентов, дисциплину структуры держим сами.
- **Все ресурсы в составе решения:** нет CDN, веб-шрифтов и картографических плиток. Внешние ресурсы на машине судьи доступны, но «критичные файлы рекомендуется размещать в составе Решения» (Окружение судьи).
- **Язык интерфейса — русский.** Работники обозначены условными кодами («Р-07»), без имён: персональные данные запрещены (Правила; `SUBMISSION.md`, строка 49).
- **Постоянная надпись** в верхней строке, которую нельзя скрыть: «Синтетические данные. Расчёт модели, не сведения о реальной шахте».

### 2.2. Три независимые оси состояния

Интерфейс никогда не сливает эти оси в один «статус» и один цвет. Цвет — вторичный признак; каждое значение имеет форму, штриховку или значок и текст и должно читаться на снимке в оттенках серого.

| Ось | Значение | Смысл | С чем нельзя путать | Обозначение | Текст на экране |
|---|---|---|---|---|---|
| Опасность (участок, выработка) | `normal` | Синтетический индекс нестабильности ниже порога «внимание» по актуальным данным | С «безопасно» в реальной шахте; с отсутствием данных | Сплошная светлая заливка полосы выработки, без значка | «норма» |
| | `attention` | Индекс или скорость смещения выше порога «внимание» | С аварией; с устаревшими данными | Редкая косая штриховка, треугольный значок | «внимание» |
| | `danger` | Выше порога «опасно» | С вероятностью обрушения; с закрытым проходом | Плотная перекрёстная штриховка, толстый контур, значок-восьмиугольник | «опасно» |
| Знание (качество данных) | `fresh` | Возраст измерения в модельных секундах в пределах допуска | С «норма»: свежие данные могут показывать опасность | Обычный значок датчика | «данные актуальны» |
| | `stale` | Возраст измерения больше допуска `stale_after_s` | С потерей; с остановкой всей модели | Значок датчика с часами; участок подписан «по устаревшим данным» и не рисуется как «норма» | «данные устарели» |
| | `lost` | Измерений нет дольше `lost_after_s` | С нулевым показанием | Перечёркнутый значок датчика, пунктирный контур | «данные потеряны» |
| | `unknown` (итог для участка) | Данным, на которых стоит состояние, нельзя верить | С «норма» и с «опасно» | Полоса без заливки с пунктирным контуром, значок «?» | «состояние неизвестно» |
| | `none` | У выработки нет датчиков по построению модели | С «норма» и с потерей датчика | Тонкая линия без заливки и значков | «без датчиков, состояние не оценивается» |
| Достижимость (работник) | `ok` | В графе модели есть открытый путь до выхода | С подтверждённо безопасным путём | Круглая метка с кодом; у выбранного — линия маршрута со стрелками | «расчётный маршрут (модель): 412 м» |
| | `none` | В графе модели нет открытого пути | С гибелью, блокировкой или опасностью; это утверждение о графе модели, а не о реальном мире | Квадратная перечёркнутая метка | «нет расчётного маршрута» |
| | `unknown` | Маршрут не рассчитан или положение неизвестно | С «нет маршрута» | Пустая пунктирная метка со знаком «?» | «маршрут не рассчитан» |
| Достижимость (выработка) | `open` / `closed` | Проходимость ребра графа | С опасностью: закрытая выработка может быть в норме | Закрытая: разрыв полосы и поперечный барьер с крестом | «проход открыт» / «проход закрыт» |
| Достижимость (выход) | `available` / `unavailable` / `unknown` | Можно ли завершить маршрут в этом выходе | С числом вышедших | Значок выхода: целый, перечёркнутый, с «?» | «выход доступен (модель)» / «выход недоступен» / «состояние выхода неизвестно» |

Правила формулировок:

| Пишем | Никогда не пишем | Почему |
|---|---|---|
| «расчётный маршрут (модель)» | «безопасный путь», «безопасный маршрут» | Маршрут — кратчайший открытый путь в графе модели; пригодность для реальной эвакуации не проверялась ([team/PLAN.md](../PLAN.md), строка 87) |
| «синтетический индекс нестабильности» (безразмерный, 0–1) | «вероятность обрушения», «риск обрушения, %» | Индекс не откалиброван и не является вероятностью |
| «нет расчётного маршрута» | «выхода нет», «заблокирован» | Это утверждение о графе модели |
| «прогноз модели» | «ожидаемый результат», «будет» | Прогноз — тот же расчёт при неизменных условиях |
| «состояние неизвестно» | пустое место или «норма» по умолчанию | Отсутствие данных не равно норме |

Сочетания, которые обязаны различаться на экране:

| Случай | Что видно | Текст в карточке и в списке |
|---|---|---|
| Работник в нормальной зоне без маршрута | Квадратная перечёркнутая метка на полосе со сплошной светлой заливкой | «Р-07 · нет расчётного маршрута · участок: норма» |
| Работник в опасной зоне с маршрутом | Круглая метка с двойным кольцом на полосе с плотной штриховкой, линия маршрута до выхода | «Р-03 · расчётный маршрут (модель): 655 м · участок: опасно» |
| Участок, единственный датчик которого потерян | Полоса без заливки с пунктирным контуром и «?», перечёркнутый датчик | «Участок В · состояние неизвестно: данные датчика Э-05 потеряны» |

Никогда не сворачиваются: надпись о синтетических данных, состояние связи и возраст данных, три числа инцидента, легенда и разделение двух групп левой панели.

### 2.4. Иерархия

0. **Можно ли верить экрану.** Заметно только при нарушении: платформа недоступна, модель не продвигается, кадр неполный. В этом случае признак перекрывает всё остальное (раздел 4).
1. **Где опасность и сколько людей затронуто.** Полоса инцидента с тремя числами и выделенный участок на схеме. Три числа: работников в опасных зонах, без расчётного маршрута, с неизвестным состоянием. Числа считает симуляция; один работник может входить в несколько из них, это подписано.
2. **Люди и выходы.** Метки работников, их достижимость, состояние выходов, закрытые выработки.
3. **Решение.** Панель вариантов с прогнозом и кнопкой запуска, затем подтверждение исполнения.
4. **Контекст.** Условия сценария, журнал, сравнение прогонов, карточка выбранного объекта.

### 2.5. Области и слои

- **Верхняя полоса** (всегда видна): надпись о синтетических данных; состояние связи с платформой; возраст данных; модельное время, тик и коэффициент ускорения; идентификатор прогона и seed; активные условия сценария; полоса инцидента. Без инцидента полоса остаётся и пишет «Инцидентов нет» с теми же тремя числами.
- **Схема** (самая большая область). Слои снизу вверх: плоскости горизонтов с подписью отметки; выработки (рёбра) с опасностью и проходимостью; участки работ; датчики; выходы; работники; маршрут выбранного работника или участка; подписи. Работники на одном отрезке выработки объединяются в одну метку со счётчиком («×3»); объединение идёт по выработке и отрезку смещения, а не по расстоянию на экране, чтобы результат был одинаков в любом окне. Легенда видна всегда.
- **Постоянный расчёт выхода.** У каждого работника всегда есть текущий расчётный маршрут до выхода, даже когда он работает. Поэтому последствия закрытой выработки видны до того, как отдан приказ о выводе.
- **Правая панель** зависит от контекста: по умолчанию сводка смены; при выборе объекта — его карточка (значения с единицами из Ditto, модельное время измерения, время обновления платформы, причина состояния); при активном инциденте — панель решения (варианты с прогнозом, запуск, подтверждение).
- **Левая панель** видимо разделена на две группы, которые нельзя перепутать. «Условия сценария (стенд)» — что происходит с шахтой: закрыть выработку, потерять связь с датчиком, запустить рост нестабильности; рядом с каждым активным условием его отмена. «Действия диспетчера» — что решает человек: остановить участок, вывести персонал участка, возобновить работу. Отдельно — полный сброс прогона с подтверждением. Группы различаются заголовком, рамкой и формой кнопок, а не только цветом.
- **Нижняя область:** журнал событий в модельном времени (условие задано или отменено, порог пересечён, команда отправлена, применена или отклонена, работник достиг выхода) и вкладка сравнения завершённых прогонов.
- **Вид «Список»** — те же объекты простой таблицей: тип, код, место, опасность, знание, достижимость, значение с единицей, модельное время, время платформы. Он позволяет проверить данные, не читая графику, и строится из того же набора данных, что и схема.
- **Ссылка на вид** через фрагмент URL: `#/scheme?sel=<thingId>&view=axo`, `#/scheme?view=plan&level=<id>`, `#/list?type=worker`, `#/runs`. Ссылки только открывают вид и выбирают объект. Команды из URL не отправляются никогда: иначе перезагрузка страницы повторяла бы происшествие.

### 2.6. Действия

UI блокирует кнопку только по условию, которое читается из одного поля двойника, по состоянию связи или по своей неподтверждённой команде. Все остальные отказы приходят от симуляции как отклонённая команда с кодом причины: правила допустимости не дублируются в браузере.

| Действие диспетчера | Где | Предусловие | Команда (`type`, `target`) | Что подтверждает |
|---|---|---|---|---|
| Выбрать объект, увидеть маршрут | Схема, список | нет | не отправляется | Открыта карточка, изменился фрагмент URL |
| Остановить участок | Левая панель, карточка участка | `work_state = working` | `action.stop_zone`, участок | `work_state = stopped`, `production_rate = 0`, запись журнала |
| Вывести персонал участка | Там же | `withdrawal_state` не равен `in_progress` | `action.withdraw_zone`, участок | `withdrawal_state = in_progress`, у работников `status = moving_to_exit` |
| Запустить вариант | Панель решения | Инцидент активен, вариант предложен | `action.execute_option`, вариант | У варианта `state = executing`, у инцидента `selected_option` |
| Возобновить работу | Левая панель, карточка участка | `work_state = stopped` | `action.resume_zone`, участок | `work_state = working` |
| Сравнить завершённые прогоны | Вкладка внизу | нет | не отправляется | Таблица из двойников прогонов |

| Условие сценария (стенд) | Задать | Отменить | Что подтверждает |
|---|---|---|---|
| Закрыть выработку | `condition.close_working`, выработка | `condition.open_working` | `passability`, список `conditions` управляющего двойника |
| Потерять связь с датчиком | `condition.sensor_lost`, датчик | `condition.sensor_restored` | `link_state`, затем `quality` |
| Рост нестабильности | `condition.instability_on`, участок | `condition.instability_off` | Показания датчиков, затем `hazard_state` участка |
| Полный сброс прогона | `run.reset` после подтверждения в диалоге | не отменяется | Новый `idSimulationRun`, `run_state = running` |

Готовые пресеты (например, «Закрыть В-12: обход есть» и «Закрыть В-07: пути нет») приходят из данных двойников, а не зашиты в UI. Любую выработку можно также закрыть, выбрав её на схеме.

## 3. Пользовательский путь: перекрытие прохода

Участок В на горизонте −380 м тупиковый, единственный подход к нему — выработка В-07. Ветка «обход есть» закрывает В-12, ветка «пути нет» закрывает В-07. На стенде один человек играет две роли: оператор стенда задаёт условие, диспетчер принимает решение; экран их разделяет.

| UI отправляет | `run.reset` |
| Данные двойников | `run_state = resetting`, затем новый `idSimulationRun` (`run-0004`) с тем же seed, тик 0, все двойники в исходном состоянии, `conditions` пуст. Двойник `run-0003` получает `state = finished` и сохраняется. История в InfluxDB остаётся и разделяется тегом `idSimulationRun` (`deploy/compose/telegraf/telegraf.conf`, строки 43–45) |
| На экране | Надпись «Выполняется сброс» до первого полного кадра нового прогона, затем экран шага 1. Во вкладке «Сравнение прогонов» появилась строка run-0003 |
| Проверка на стенде | После сброса путь повторяется с шага 1 и даёт те же значения на тех же тиках (тот же seed) |

Повторное нажатие и повторная отправка. Пока команда не подтверждена, её кнопка заблокирована. Повтор после тайм-аута уходит с тем же `command_id`; симуляция отвечает той же записью и не создаёт второе событие, в журнале остаётся одна запись.

## 4. Состояния интерфейса

Жёсткие правила. Когда платформа недоступна, схема заморожена и видимо помечена временем последних данных; локальная анимация не продолжается; ни одно состояние не показывается нормальным по умолчанию. Неизвестное значение перечисления из платформы показывается как «неизвестно», а не как норма. Тревожные состояния не мигают.

| Состояние | Условие в данных | Что показано | Что заблокировано | Точный текст | Как снимается | Как воспроизвести |
|---|---|---|---|---|---|---|
| Нет маршрута | У работника `egress_status = none` | Квадратная перечёркнутая метка; число в полосе инцидента | Ничего | «Р-07: нет расчётного маршрута. В графе модели нет открытого пути до выхода» | `egress_status = ok` | Пресет «Закрыть В-07» |
| Датчик потерян | У датчика `quality = lost`; у участка без других актуальных датчиков `hazard_state = unknown` | Перечёркнутый датчик; участок без заливки с «?» | Ничего; прогноз вариантов помечен «по неполным данным» | «Э-05: данные потеряны. Последнее измерение 02:08:20 модельного времени» и «Участок В: состояние неизвестно» | `quality = fresh` | Условие «Потерять связь с датчиком», подождать `lost_after_s` модельных секунд |
| Устаревшие данные одного объекта | У датчика `quality = stale`; либо тик двойника отстаёт от тика кадра больше чем на 3 | Значок часов на объекте; участок подписан «по устаревшим данным» и не рисуется как «норма»; при отставании тика состояние объекта показано как неизвестное | Ничего | «Данные устарели: измерение 02:14:10, сейчас 02:15:20» или «Двойник отстаёт: тик 806 из 812» | Свежее измерение; тик догнал кадр | Первое — тем же условием до истечения `lost_after_s`; второе — на имитаторе (раздел 6.2) |
| Модель не продвигается | Ditto отвечает, тик не меняется, `Date` − `_modified` управляющего двойника больше 5 с | Схема заморожена, штриховая рамка, полоса во всю ширину | Все команды | «Модель не обновляется с 09:02:11 UTC. Показано последнее состояние: тик 812» | Тик вырос | Остановить контейнер симулятора (команду даёт Codex) |
| Ditto недоступен | Три опроса подряд: ошибка сети, тайм-аут 3 с или HTTP 401, 5xx | То же и код ошибки; переходы положения остановлены | Все команды | «Платформа недоступна (HTTP 502). Показаны данные на 09:02:11 UTC, тик 812. Текущее состояние неизвестно» | Первый полный кадр | `docker compose -f deploy/compose/docker-compose.yml stop ditto-nginx`, затем `start` |
| Команда отправлена, не подтверждена | POST принят, записи с этим `command_id` ещё нет | Цель команды с пунктирной меткой и часами; настоящее состояние объекта не меняется | Та же команда для той же цели | «Команда отправлена, не подтверждена (2 с)» | Запись `applied` или `rejected` | Любая команда; чтобы задержать — остановить симулятор |
| Команда отклонена | Запись со `status = rejected` | Сообщение у кнопки и запись в журнале; объект в прежнем состоянии | Ничего | «Команда отклонена: выработка уже закрыта (already_in_state)» | Закрыть сообщение или отправить новую команду | Имитатор; на стенде — команда с несуществующей целью через `curl` (видна в журнале) |
| Нет подтверждения | Записи нет дольше 5 с настенного времени | Предупреждение у кнопки, две кнопки | Ничего | «Нет подтверждения 5 с. Команда могла не дойти» — «Повторить с тем же идентификатором», «Снять ожидание» | Запись появилась или ожидание снято | Остановить симулятор, отправить команду |
| Команда не отправлена | POST вернул ошибку | Сообщение у кнопки | Ничего | «Команда не отправлена: платформа недоступна (HTTP 502)» | Повторная отправка | Остановить `ditto-nginx`, нажать кнопку до срабатывания блокировки |
| Неполный кадр | Часть двойников отстаёт от тика управляющего двойника на 1–3 тика | Значок часов на отставших объектах, счётчик в верхней полосе | Ничего | «Кадр неполный: 2 объекта отстают от тика 812» | Все двойники на тике кадра | Имитатор: потерю сообщения QoS 0 на стенде не вызвать намеренно |
| Сброс выполняется | Своя неподтверждённая `run.reset` или `run_state = resetting` | Надпись поверх приглушённой схемы | Все команды | «Выполняется сброс. Новый прогон ещё не начался» | Новый `idSimulationRun`, `run_state = running`, полный кадр | Кнопка «Полный сброс прогона» |
| Несовпадение версии топологии | `topology_version` шахты и управляющего двойника различаются после повторной загрузки атрибутов | Схема не рисуется; вид «Список» доступен | Все команды | «Схема не показана: версия топологии в двойниках (t2) не совпадает с версией модели (t1)» | Версии совпали | Имитатор; на стенде — запуск симулятора с другой топологией без пересоздания двойников |
| Пустой стенд | Двойник шахты не найден или поиск вернул 0 объектов | Сообщение на месте схемы; никаких демонстрационных данных | Все команды | «Двойники рудника не найдены в платформе. Платформа отвечает, объектов в `<ns>` нет» | Двойники появились | Платформа без сервисов команды или до завершения создания двойников |

## 5. Предложение контракта данных

Это предложение для Codex, а не существующий API. Пространство имён обозначено `<ns>`; предлагаю `team040.mine`.

### 5.1. Общие правила

- Форма признака — как в платформе: `"features": {"<имя>": {"properties": {"value": <число или строка>, "unit": "<единица>"}}}` (`examples/mine/twins.json`). Двойники создаются идемпотентным `PUT /api/2/things/{id}` с политикой `default:basic_policy` (`examples/mine/setup_twins.py`).
- **Атрибуты** статичны: их задаёт создание двойников и не меняет прогон. **Признаки** динамичны: их публикует симулятор каждым тиком полной заменой `/features` (`OPENEGIZ.ru.md`, строка 114). UI в Ditto ничего не пишет, кроме сообщения команды.
- Каждый двойник, который публикует симулятор, несёт три общих признака: `tick`, `sim_time_s`, `idSimulationRun`. Обогащение событий берёт `idSimulationRun` у того двойника, о котором событие (`deploy/compose/init/mosquitto-target-connection.json`, строка 13; по документации Ditto, на стенде не проверено), поэтому тег прогона в истории появится только у двойников со своим таким признаком.
- Управляющий двойник `shift` публикуется в тике последним. Кадр полон, если у всех динамических двойников `tick` равен `tick` двойника `shift`.
- Нет `null` и условных значений вроде −1 или 0. Признак, не имеющий смысла в текущем состоянии, не публикуется; UI показывает «—».
- При потере связи значение датчика не обнуляется и не удаляется: остаётся последнее измерение с его временем.
- `hazard_state = normal` допустимо только при `data_quality = fresh` ([team/PLAN.md](../PLAN.md), строка 79). Сохранять ли `attention` и `danger` при неактуальных данных, решает модель (вопрос 10). Если `normal` придёт с неактуальными данными, UI покажет «состояние неизвестно».
- Ссылки на другие двойники — локальное имя без `<ns>`. Исключение — `_parents`, где платформа ждёт полный `thingId`.
- Атрибут `label` — код для экрана («В-12», «Э-05», «Р-07»). UI не придумывает имён.
- Списки — массив в `value`. Как массивы и объекты проходят через Telegraf, не проверено; запасной вид — строка через запятую, а для записей — поля через двоеточие в фиксированном порядке. Поэтому коды и идентификаторы состоят только из символов `a-z`, `0-9`, `_`, `.`, `-`.

`workers_unknown` — число работников, у которых неизвестно положение, не рассчитан маршрут или неизвестно состояние участка, где они находятся. Предлагаю не включать в него работников, которые находятся в выработке без датчиков (`data_quality = none`, `hazard_state = unknown`, `reason_code = no_sensor`): иначе каждый идущий по транспортной выработке попадает в «неизвестно», и число перестаёт что-либо значить. На экране такая выработка подписана «без датчиков, состояние не оценивается».

**`incident`**, **`option`**, **`run`**, **`journal`**

| Двойник | Поле | Тип, единица | Значения | Что делает UI |
|---|---|---|---|---|
| `incident` | `state` | строка | `none`, `active`, `executing`, `done` | Полоса инцидента и панель решения |
| | `trigger`, `zone`, `opened_at_tick`, `selected_option` | строки; целое | `hazard`, `passage_closed`, `data_lost`; участок; тик; вариант | Заголовок панели |
| `option` | `option_kind` (А) | строка | `observe`, `stop_withdraw_zone`, `withdraw_level`, `withdraw_all` | Подпись варианта; неизвестный код выводится как есть |
| | `state`, `scope` | строка; массив | `inactive`, `offered`, `executing`, `done`, `unavailable`; участки | Строка таблицы и кнопка запуска |
| | `forecast_tick`, `forecast_quality` | целое; строка | тик расчёта; `full`, `partial` | «прогноз модели на тик N», «по неполным данным» |
| | `forecast_last_out_s`, `forecast_in_danger`, `forecast_no_route`, `forecast_downtime_s` | с; целое; целое; с | прогноз по четырём показателям | Таблица вариантов |
| | `actual_last_out_s`, `actual_in_danger`, `actual_no_route`, `actual_downtime_s` | то же | факт после исполнения | Столбец «факт прогона» рядом с прогнозом |
| `run` | `state`, `seed`, `scenario_key`, `conditions`, `executed_option` | строки; целое | `running`, `finished`; ключ одинаковых условий | Группирует сравнимые прогоны; иначе «условия отличаются» |
| | `last_out_s`, `in_danger`, `no_route`, `downtime_s`, `finished_at_sim_s` | с; целые; с | итог прогона | Таблица сравнения |
| `journal` | `last_seq` | целое | номер последнего события, растёт всегда, в том числе после сброса | Находит пропуски |
| | `events` | массив записей | последние 50: `seq`, `run`, `tick`, `sim_time_s`, `code`, `subject`, `arg`, `command_id` | Тексты составляет UI по кодам; неизвестный код выводится как есть |

Варианты предлагаю делать отдельными двойниками с плоскими числовыми признаками, а не массивом внутри `incident`: они проходят через Telegraf без вопросов о массивах, и прогноз получает историю в InfluxDB. Двойники `run` переживают сброс. Определения показателей: `last_out_s` — модельные секунды от применения команды до выхода последнего работника, у которого есть маршрут; `in_danger` — число работников в зонах `danger` в конце расчёта; `no_route` — число работников без маршрута; `downtime_s` — суммарный простой остановленных участков.

Коды журнала: `run.started`, `run.reset`, `condition.set`, `condition.cancelled`, `hazard.changed`, `quality.changed`, `command.applied`, `command.rejected`, `zone.stopped`, `zone.resumed`, `withdrawal.started`, `withdrawal.finished`, `worker.route_changed`, `worker.no_route`, `worker.out`.

### 5.4. Чтение

```text
1. Список двойников (при загрузке и после сброса):
   GET /ditto/api/2/search/things?namespaces=<ns>&fields=thingId&option=size(200)
   следующая страница: option=size(200),cursor(<cursor из ответа>)
2. Атрибуты (при загрузке и при смене topology_version):
   GET /ditto/api/2/things?ids=<все идентификаторы>&fields=thingId,attributes,_revision
3. Состояние (около 1 раза в секунду):
   GET /ditto/api/2/things?ids=<динамические двойники>&fields=thingId,features,_modified,_revision
```

- Поиск отдаёт результаты страницами (по умолчанию 25, не больше 200, далее по курсору), и его индекс согласован с задержкой (по документации Ditto, на стенде не проверено). Он годится для списка, но не для текущих значений. Полноту списка UI сверяет с `counts`; при расхождении повторяет поиск и показывает «состав двойников неполный».
- Порядок объектов в ответе на запрос по `ids` не гарантирован: UI индексирует по `thingId`.
- Оценка объёма, не измерение: около 75 двойников (36 выработок, 4 участка, 10 датчиков, 14 работников, 3 выхода и служебные), идентификаторы около 2 КБ в строке запроса, ответ 30–50 КБ. Заголовки запроса ограничены буферами nginx (`deploy/compose/ditto/nginx.conf`, строки 16–17); при росте числа двойников запрос делится на части, и кадр собирается только из полного набора частей.
- Если в ответе есть двойники с тиком больше, чем у `shift`, опрос попал в середину публикации тика: UI повторяет запрос через 200 мс, не больше двух раз.
- Новый опрос не начинается, пока не завершён предыдущий; тайм-аут запроса 3 с.

### 5.5. Команда и подтверждение

```text
POST /ditto/api/2/things/<ns>:shift/inbox/messages/command?timeout=0
Content-Type: application/json
ожидаемый ответ: 202 без тела (по документации Ditto, на стенде не проверено)
```

Поля тела: `command_id` (создаётся в браузере, вид `c-` и 16 шестнадцатеричных цифр), `type`, `target`, `run` (прогон, который видел UI; команда для другого прогона отклоняется). Ditto пересылает сообщение в топик `opentwins/live/messages/<ns>/shift` (`deploy/compose/init/mosquitto-target-connection.json`, строки 10 и 14); политика `default:basic_policy` разрешает сообщения (`deploy/compose/init/basic-policy.json`, строки 31–37).

Подтверждение — запись в признаке `commands` двойника `shift` и событие журнала с тем же `command_id`. Поля записи: `id`, `type`, `target`, `status` (`applied` или `rejected`), `tick`, `sim_time_s`, `reason`. Коды `reason`: `none`, `unknown_type`, `unknown_target`, `already_in_state`, `not_allowed_in_state`, `invalid_run`, `malformed`. Повтор с известным `command_id` возвращает прежнюю запись и ничего не меняет. Ожидающие команды UI держит в памяти страницы; после перезагрузки истиной остаётся состояние двойников.

Целевые задержки. Это цели для измерения на стенде, а не обещания и не результаты:

| Отрезок | Цель | Основание |
|---|---|---|
| Публикация симулятора → значение в Ditto | около 1 с | оценка для платформы, не измерено |
| Значение в Ditto → экран | не больше 2 с | период опроса 1 с и отрисовка |
| Нажатие → подтверждение на экране | не больше 3 с | один тик симуляции и один опрос |
| Порог «нет подтверждения» | 5 с настенного времени | не меньше трёх тиков |
| Порог «модель не продвигается» | 5 с без нового тика | не меньше трёх периодов `tick_wall_ms`; у заголовка `Date` точность 1 с |
| Порог «платформа недоступна» | три неудачных опроса подряд | |
| История в InfluxDB и Grafana | не раньше чем через 10 с | `deploy/compose/telegraf/telegraf.conf`, строки 5 и 10; UI её не читает |

### 5.7. Открытые вопросы к Codex

1. **Канал команд.** Вариант А — live-сообщение во входящие `shift` (раздел 5.5); вариант Б — двойник желаемого состояния, которым владеет UI (пробел 1.2). Какой выбираем?
2. **Массивы и объекты в значениях признаков.** Как их разбирает Telegraf (`json_v2`), не проверено. Если плохо, `route`, `conditions`, `runs`, `commands` и `events` переходят на строку через запятую. Нужна проверка на стенде 13–14 октября.
3. **Пространство имён.** Подходит ли `team040.mine` и схема локальных имён (`w-12`, `zone-c`, `sens-ext-05`, `worker-07`)?
4. **Где живёт прогноз и когда открывается инцидент.** Двойники `option`, как в разделе 5.2, или иначе? Какие варианты модель предлагает и какие события открывают инцидент?
5. **Число двойников и список.** Сколько двойников и сообщений в секунду выдерживает стенд? Есть ли предел числа `ids` в одном запросе? Достаточно ли поиска со сверкой по `counts`, или надёжнее список идентификаторов в атрибуте шахты?
6. **Засоряют ли live-сообщения InfluxDB.** Telegraf подписан на `opentwins/#`, а его тег `extra.thingId` не помечен необязательным (`deploy/compose/telegraf/telegraf.conf`, строки 32–34). У live-сообщения поля `extra` нет; допущение — ошибка разбора в журнале Telegraf на каждую команду, а не точка в базе. Проверить, а также убедиться, что заголовок `Authorization`, подставленный прокси, не попадает в MQTT (список исключаемых заголовков: `deploy/compose/docker-compose.yml`, строки 31–33 и 71–78).
7. **Масштаб времени.** Сколько настенного времени занимает вывод на стенде? Условно: 655 м при 1,25 м/с — это 524 модельные секунды, то есть почти 9 минут без ускорения и около 52 с при ×10. Какой шаг тика и какое ускорение выбираем, и нужна ли кнопка смены скорости?
8. **Сброс и двойники прогонов.** Как создаётся двойник `run` (через MQTT или HTTP), что с ним делает сброс и сколько прогонов храним?
9. **Одинаковый момент условия в сравниваемых прогонах.** Условие, заданное кнопкой, попадает на разный тик. Применять его на фиксированном модельном времени после сброса или считать прогоны сравнимыми при разном моменте и показывать момент в таблице?
10. **Правила модели, видимые на экране.** Возвращаются ли работники на участок после `action.resume_zone`? Обходит ли расчёт маршрута зоны `danger` или только закрытые выработки? Что происходит с `attention` и `danger`, когда данные участка устарели: состояние сохраняется с пометкой или становится `unknown`?
11. **Показатель «в опасной зоне».** Число работников в конце расчёта или человеко-секунды пребывания в зонах `danger`? Второе точнее различает варианты.

## 6. Проверка без GPU и объём работы

### 6.1. Проверяемые критерии

Бюджеты — цели для измерения на Ubuntu 24.04 с 8 vCPU без GPU (Окружение судьи), а не измеренные результаты.

| 15 | Объём статических файлов | Суммарный размер без сжатия | не больше 300 КБ |

### 6.2. Имитатор для тестов

Небольшой сервер на стандартной библиотеке Python 3 раздаёт те же статические файлы и отвечает на тех же путях `/ditto/...` записанными ответами Ditto; для POST возвращает 202 и по сценарию добавляет запись подтверждения. Боевой UI не содержит ни ветки для подставных данных, ни скрытых демонстрационных значений ([team/PLAN.md](../PLAN.md), строка 67): тот же код, отличается только origin. До появления двойников на стенде ответы составляются вручную по разделу 5 и помечаются «составлено по проекту контракта»; после 15–16 октября они заменяются записанными со стенда. Средства тестирования (headless Chromium) нужны только разработке и не входят в запуск решения.

## 7. Предлагаемые общие изменения вне team/ui/

Только предложения; в этом проходе изменён один файл, `team/ui/DESIGN.md`.

1. **Overlay-файл compose с сервисом UI** (например, `team/compose.yml`): nginx со статикой и прокси `/ditto/`, переменная `DITTO_BASIC_AUTH`, порт `127.0.0.1:${TEAM_UI_PORT:-8088}`. Причина: без этого страница не читает Ditto без пароля в браузере (пробел 1.5). Образец подключения — `examples/mine/compose.yml`. Прокси должен заново разрешать имя `ditto-nginx` через DNS Docker (`resolver 127.0.0.11` и адрес в переменной): nginx по умолчанию запоминает адрес при старте, и после пересоздания контейнера `ditto-nginx` состояние «Платформа недоступна» могло бы не сняться.
2. **Подключение overlay-файла в `Makefile`** по образцу строк 6–12. Причина: решение должно подниматься той же командой, что и платформа, без ручных шагов.
3. **Вывод адреса UI** в `scripts/compose-urls.sh` и проверка его доступности в `scripts/compose-smoke.sh`. Причина: адрес интерфейса должен быть виден после запуска и проверяться вместе со стендом.
4. **Уточнения в `team/PLAN.md`:** разделить прогноз вариантов и сравнение завершённых прогонов (строки 15–16 и 36); назвать канал команд (строка 54); назвать трое часов и отметку кадра (строка 53); указать, что геометрия хранится в двойниках (строки 23 и 51); указать адрес и способ доступа UI (строки 52 и 55). Причина: пять пробелов раздела 1.
5. **`deploy/compose/telegraf/telegraf.conf`** — только если проверка вопроса 6 покажет ошибки разбора live-сообщений. Причина: каждая команда не должна давать ошибку в журнале платформы.
6. **`SUBMISSION.md`**, разделы о визуализации и сценариях: адрес интерфейса, ссылки на виды, способ увидеть и отменить каждый сценарий (Правила, пункт 6.12). Причина: заполняется командой после проверки на стенде, не раньше.
