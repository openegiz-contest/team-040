# Контрактные фикстуры и тестовый сервер

**Все числа в этом каталоге придуманы для тестов и не являются измерениями стенда.** Рудник условный, его геометрия, показания датчиков, скорости, прогнозы и времена сочинены, чтобы проверить интерфейс по [team/CONTRACT.md](../../CONTRACT.md). Это не результат работы сервиса симуляции команды.

**Тестовый сервер — не симулятор.** `tools/mock_server.py` воспроизводит записанные кадры и не содержит логики рудника: положения, маршруты, состояния и числа берутся только из файлов `fixtures/*.json`. Боевой код интерфейса к `/__mock__/` не обращается и о фикстурах не знает.

Файлы `*.json` создаёт `tools/build_fixtures.py`; руками их не правят.

## Запуск

Все команды выполняются из корня репозитория. Нужен только Python 3 (стандартная библиотека).

```text
python team/ui/tools/build_fixtures.py            пересобрать fixtures/*.json
python team/ui/tools/build_fixtures.py --check    код возврата 1, если файлы отличаются от свежей сборки
python team/ui/tools/mock_server.py --port 8088 --scenario normal
python team/ui/tools/mock_server.py --port 0      свободный порт
python -m unittest discover -s team/ui/tests -t team/ui -p "test_mock_server.py" -v
```

Первая строка вывода сервера — `LISTENING http://127.0.0.1:<порт>`. Сервер слушает только 127.0.0.1 и останавливается по Ctrl+C. Страница управления: `http://127.0.0.1:<порт>/__mock__/`.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--port` | 8088 | 0 — выбрать свободный порт |
| `--scenario` | `normal` | имя файла фикстуры без `.json` |
| `--publication-ms` | 1000 | настенная длительность одной публикации. Меньшее значение нужно только тестам, чтобы не ждать: длинный вывод людей при 100 мс проходит за 6 с вместо 58 с. Зависание POST из сценария `commands` масштабируется так же. Контрактное значение — 1000 |
| `--public-dir` | `team/ui/public` | каталог, который раздаётся по `/` |
| `--fixtures-dir` | `team/ui/fixtures` | каталог с фикстурами |

Сборка детерминирована: без часов и случайных чисел, ключи отсортированы, концы строк LF. Повторный запуск даёт те же байты. Git с `core.autocrlf=true` при извлечении может заменить LF на CRLF; `--check` и тесты сравнивают без учёта этой замены.

## Базовый рудник

Определён один раз в классе `Mine` генератора; каждый сценарий получается из него явными изменениями в коде генератора.

| Вид | Идентификаторы | Подписи |
|---|---|---|
| `mine`, `shift`, `incident`, `journal` | `mine`, `shift`, `incident`, `journal` | «Рудник (условный)», «Смена», «Инцидент», «Журнал» |
| `level` | `level-260`, `level-320`, `level-380` | «Гор. −260 м» и т. д.; отметки −260, −320, −380 м |
| `working` | `w-01` … `w-36` | «В-01» … «В-36» |
| `zone` | `zone-a` … `zone-d` | «Участок А», «Участок Б», «Участок В», «Участок Г» |
| `sensor` | `sens-ext-01…05`, `sens-conv-01…03`, `sens-geo-01…02` | «Э-01…05», «К-01…03», «Г-01…02» |
| `worker` | `worker-01` … `worker-14` | «Р-01» … «Р-14» (только коды, имён нет) |
| `exit` | `exit-shaft`, `exit-ramp`, `exit-raise` | «Ствол», «Съезд», «Восстающий» |
| `option` | `option-observe`, `option-stop-withdraw`, `option-withdraw-all` | «Вариант 1…3»; `option_kind` = `observe`, `stop_withdraw_zone`, `withdraw_all` |
| `run` (архив, не в `manifest`) | `run-0001` … `run-0004`; после сброса `run-0005` | |

В `manifest` 77 идентификаторов, в `dynamic_ids` 72 (всё, кроме `mine`, `shift` и трёх `level`). Текущий прогон — `run-0005`, seed 42, ускорение ×10.

Геометрия: локальные метры, x и y — план, z — отметка. У всех горизонтов общая система координат, уровень занимает около 560 × 220 м.

- Ствол на (80, 120): `w-02` (−380 → −320) и `w-01` (−320 → −260), по 60 м.
- Съезд на востоке, один прямоугольный виток между горизонтами: `w-04` (−380 → −320) и `w-03` (−320 → −260), по 303 м; отметка растёт вдоль `points`.
- Запасный восстающий `w-05` с гор. −380 прямо на гор. −260, 120 м.
- Выходы — три узла `node_kind = exit` на гор. −260: `n-01` (ствол), `n-06` (съезд), `n-03` (восстающий). Выше гор. −260 модель рудника не продолжается.
- Участок А — `w-32…w-36` (гор. −260); участок Б — `w-13…w-17` (гор. −320); участок В — `w-20`, `w-21` (гор. −380, тупик за `w-07`); участок Г — `w-23…w-25` (гор. −380).
- Выработки без участка (`w-01…w-12`, `w-18`, `w-19`, `w-22`, `w-26…w-31`) не имеют датчиков: `hazard_state = unknown`, `data_quality = none`, `reason_code = no_sensor`, `routing_restriction = allowed`.
- У `w-16`, `w-23`, `w-03`, `w-04` непустой `points`: положение работника — доля `offset_m / length_m` вдоль ломаной, а не вдоль хорды.
- Межгоризонтная выработка записана на нижний из своих горизонтов (`level` и `_parents`).

`length_m` каждой выработки равна длине её ломаной в трёх измерениях с точностью до 1 м. `egress_length_m` в каждом кадре равна остатку текущей выработки до `route_next_node` плюс сумме `length_m` остальных выработок маршрута; `egress_eta_s` = длина / 1,25 м/с, округление до ближайшего целого. Тесты проверяют оба правила для каждого кадра.

История из раздела 3 [DESIGN.md](../DESIGN.md) в числах фикстуры:

| Что | Значение |

## Что фикстуры доопределяют сами

Контракт эти места не фиксирует. Здесь выбран один вариант, интерфейс не должен на него полагаться сильнее, чем на контракт; список передан как вопросы к контракту.

- `tick` считает модельные секунды: за публикацию `tick` и `sim_time_s` растут на 10.
- `location_hazard` работника повторяет `hazard_state` выработки, где он находится. В выработке без датчиков это `unknown`; почему — видно по `data_quality = none` этой выработки. В `workers_unknown` такие люди не входят.
- `egress_crosses` — худшее состояние среди выработок маршрута, входящих в участки; если таких выработок на маршруте нет, признак не публикуется.
- `egress_detour_m` и `egress_detour_s` считаются от текущего положения: длина маршрута минус длина кратчайшего пути при всех открытых выработках.
- У вышедшего работника (`status = out`) есть `at_exit`, `egress_status = ok`, `egress_reason = none`; нет `at_working`, `offset_m`, `location_hazard` и признаков маршрута.
- `last_known_hazard_state` и `last_known_hazard_tick` публикуются, только когда `data_quality` не `fresh`.
- У `incident` есть массив `causes` из записей `{"trigger", "subject", "tick"}`; `trigger` и `zone` относятся к первой причине.
- Невыбранные варианты получают `state = unavailable` и сохраняют свой прогноз.
- Показатели `forecast_*` и `actual_*` считаются от точки решения до завершения варианта (вывод закончен или признан неполным) либо до горизонта 900 с. Прогноз — исход копии состояния по тому же сценарию, поэтому без вмешательства факт равен прогнозу.
- Вывод, в котором оставшиеся люди не имеют маршрута, становится `incomplete` на следующей публикации; вариант получает `done`, инцидент — `done`.
- После завершения варианта прогон остаётся текущим, `run_state = running`, последний кадр повторяется; накопительные показатели в повторяемом кадре не растут.
- Запись подтверждения для `command_id_conflict` несёт тот же `id`, что и первая запись этой команды: в `commands` оказываются две записи с одним `id`.
- Подтверждение `run.reset` и `run.start_preset` появляется только в `commands` нового прогона, в публикациях `resetting` его ещё нет. Прогон, прерванный запуском пресета, тоже получает `completion_reason = reset`.
- Команда условия оставляет в журнале одну запись (`condition.set` или `condition.cancelled`) с `command_id`; исполнение варианта — `command.applied`. У записей журнала нет ключей `arg` и `command_id`, когда значения нет.
- В `danger_zone` участок В с неизвестным состоянием тоже получает `routing_restriction = blocked`: контракт запрещает новый вход в опасную или неизвестную зону (§7), как и в `sensor_lost_after_danger`. Устаревание датчика и рост опасности происходят на одной публикации, поэтому у инцидента две причины (`hazard`, `data_lost`); отдельного события журнала «инцидент открыт» в кодах журнала нет и фикстура его не выдумывает.
- Единицы: `downtime_s` у участка — `s`, у `shift`, варианта и прогона — `zone*s`; интегралы — `person*s`; индекс — `1`.

## Формат файла

```text
{
 "_fixture":   {"notice", "contract_version": 1, "scenario", "description"},
 "format": 1, "namespace": "team040.mine",
 "clock":      {"tick_step": 10, "follow_fields": [...], "event_fields": [...], "record_lists": {...}},
 "publication": {"first_seq", "first_revision", "freeze_at"?, "modified_age_s"?},
 "attribute_sets": {"t1": [{"thingId", "attributes"}, ...]},   порядок = manifest, первый — mine
 "archive":    [{"thingId", "attributes", "features"}, ...],   двойники run
 "start": "initial",
 "states": {"<имя>": {
     "clock": "run" | "hold",        идёт ли модельное время
     "frames": [<features двойника shift целиком, со scene>, ...],
     "publications": N,              сколько публикаций длится состояние (по умолчанию — число кадров)
     "next": "<имя>",                куда перейти после; без next последний кадр повторяется бесконечно
     "attributes": "t2",             набор атрибутов (по умолчанию первый)
     "new_run": true,                вход начинает новый прогон: модельное время берётся из кадра
     "metadata": false,              ответ shift без _modified и _revision
     "rules": [<правило команды>, ...]
 }}
}
```

Кадр — полный набор признаков `shift` в форме Ditto, внутри `scene` — весь массив состояний. Если кадров меньше, чем `publications`, повторяется последний. В сценарии `empty` нет ни состояний, ни атрибутов.

Правило команды; первое подходящее в списке текущего состояния выигрывает:

```text
{"when": {"type": "...", "target": "...", "decision_id": "..."},   все указанные поля должны совпасть с телом
 "ack": {"status": "applied" | "rejected", "reason": "...", "new_run": "run-0006"},
 "no_ack": true,          вместо ack: подтверждения не будет никогда
 "ack_delay": 2,          на сколько публикаций позже обычного показать подтверждение
 "goto": "<состояние>",   эффект: со следующей публикации идут кадры этого состояния
 "bind": "close",         запомнить command_id; строки "@close" в записях журнала заменяются на него
 "transport": [{"status": 503, "delivered": false}, {"hang_ms": 10000, "status": 504, "delivered": true}],
                          исходы первых POST по этому правилу; дальше обычный 202
 "key": "stop-zone-b"}    общий счётчик попыток transport для правил разных состояний
```

### Время

Кадры записаны на условной шкале (обычно с тика 1200), а команды приходят когда угодно, поэтому сервер ведёт модельное время сам и переносит времена кадра на фактическую шкалу. Содержание кадра при этом не меняется.

- В состоянии `run` модельное время растёт на `tick_step` за публикацию, в `hold` стоит. При переходе из идущего состояния время сдвигается на один шаг; при входе в состояние `new_run` берётся из кадра.
- `tick` и `sim_time_s` двойника `shift` и каждого элемента `scene` всегда соответствуют текущей публикации; отставание отдельного элемента, записанное в кадре, сохраняется (`invalid_mixed_tick`).
- Признаки из `follow_fields` (`measured_at_tick`, `measured_at_sim_s`, `index_at_tick`) следуют за временем элемента, если в кадре равны его `tick`; иначе это момент в прошлом.
- Моменты в прошлом — они же, признаки из `event_fields` (`opened_at_tick`, `forecast_tick`, `last_known_hazard_tick`) и поля `tick`, `sim_time_s` в записях журнала, подтверждений и причин инцидента — сдвигаются на столько, на сколько фактический вход в состояние отличался от записанного. Например, если В-12 закрыли на тике 1340, запись «условие задано», `opened_at_tick` и `forecast_tick` покажут 1340.
- `publication_seq`, `_modified`, `_revision` и записи подтверждений сервер проставляет сам; значения этих признаков в кадрах не используются.

## Поведение сервера

**Публикации.** Одна на `--publication-ms` настенного времени, считается по монотонным часам при обращении. Первая публикация сценария — в момент его запуска. `publication_seq` = `first_seq` + номер публикации − 1, `_revision` так же от `first_revision`, `_modified` — настенное время публикации в UTC. `freeze_at: N` останавливает всё на публикации N; `modified_age_s` состаривает `_modified`.

**Чтение.** `GET /ditto/api/2/things/<id>` и `GET /ditto/api/2/things?ids=…`, параметр `fields` — имена верхнего уровня (`thingId`, `policyId`, `attributes`, `features`, `_modified`, `_revision`) и простые пути `a/b`; без `fields` — как Ditto, без полей с подчёркиванием. Пакет возвращается в перемешанном порядке, который всегда отличается от порядка запроса; неизвестные идентификаторы пропускаются; больше 20 идентификаторов, отсутствие `ids` или чужое пространство имён — 400. Неизвестный двойник — 404 с телом `{"status": 404, "error": "things:thing.notfound", "message", "description"}`. Отдельный двойник из `scene` отдаётся со своими признаками из текущего кадра. Двойник `run` существует, только если он перечислен в `runs` текущего кадра. У каждого ответа есть заголовок `Date`.

**Команда.** `POST /ditto/api/2/things/team040.mine:shift/inbox/messages/command?timeout=0`.

| Проверка | Ответ |
|---|---|
| нет `timeout=0`; `Content-Type` не `application/json`; тело не JSON-объект; нет строковых `command_id`, `type`, `target`, `run`; `command_id` не `c-` и 32 строчные шестнадцатеричные цифры | 400, команда не принята |
| тело больше 4096 байт | 413, команда не принята |
| иначе | 202 без тела (если правило не задаёт `transport`) |

Принятая команда обрабатывается в таком порядке; подтверждение появляется в `commands` со следующей публикацией, его `tick` — тик этой публикации:

1. Известный `command_id` с тем же телом — ничего не выполняется, новой записи нет. С другим телом — запись `rejected`, `command_id_conflict`.
2. Неизвестный `type` — `rejected`, `unknown_type`. Цель не того вида или отсутствует в атрибутах (для `run.start_preset` — нет такого пресета) — `unknown_target`. `action.execute_option` без `decision_id` — `malformed`. `run` не равен текущему прогону — `invalid_run`.
3. Правило состояния: его `ack`, `goto`, `bind`.
4. Правила нет — `rejected` с причиной **`not_scripted`**. Такого кода в контракте нет: это ограничение фикстуры, а не отказ модели. Интерфейс покажет его как неизвестный код.

Журнал идентификаторов живёт до перезапуска сценария и переживает сброс прогона. `commands` показывает авторские записи кадра и подтверждения сервера, последние 32.

**Остальное под `/ditto/`** — 404 для неизвестного пути, 405 для другого метода на известном пути; запрос попадает в журнал с `allowed: false`. Будущий прокси ничего другого не разрешает.

**Статика.** `/` и файлы из `--public-dir` с типами для `.html`, `.css`, `.js` (`text/javascript`), `.svg`, `.json`; `Cache-Control: no-store`; `/` отдаёт `index.html`, любой каталог — 404 (списка файлов нет); путь с `..`, `.` или обратной косой чертой — 403.

### Управление: `/__mock__/`

| Вызов | Действие |
|---|---|
| `GET /__mock__/` | HTML-страница: пометка «тестовый инструмент», текущий сценарий, кнопки сценариев и сбоев, ссылка на `/` |
| `GET /__mock__/scenarios` | `{"scenarios": [{"name", "description"}], "current"}` |
| `POST /__mock__/scenario` `{"name"}` | запуск сценария с первого кадра; очищает журнал запросов, журнал идентификаторов команд и сбой. Неизвестное имя — 404 |
| `GET /__mock__/state` | `scenario`, `description`, `fault`, `interval_ms`, `elapsed_ms`, `state`, `frame_index`, `frames_in_state`, `publications_in_state`, `clock`, `publication`, `publication_seq`, `tick`, `run`, `run_state`, `attribute_set`, `frozen`, `pending_goto`, `bindings`, `acknowledgements` (все записи с признаком `visible`) |
| `GET /__mock__/log` (`?since=<n>`) | `{"entries": [...]}` — запросы к `/ditto/` и к статике по порядку; запросы к `/__mock__/` не записываются |
| `POST /__mock__/fault` `{"mode"}` | `none`, `http_502`, `http_503`, `hang` (нет ответа 30 с или до разрыва клиентом), `drop` (соединение закрывается без ответа). Действует только на `/ditto/`, включая POST: команда при сбое не принимается |

Запись журнала: `n`, `t_ms` (от запуска сценария), `method`, `path`, `kind` (`ditto`, `command`, `static`), `status`, `allowed`, при сбое `fault`. У команды дополнительно: `body`, `delivered`, `effect_applied` (правило сменило состояние), `duplicate`, `conflict`, `rule`, `goto`, `ack` (запись подтверждения или `null`), `hang_ms`. У POST, оборванного клиентом во время зависания, `status = "client_disconnected"`.

## Сценарии

### `detour` и `no_path`

Один сценарий на две ветки раздела 3 DESIGN.md. В `detour` закрывается `w-12`, участок инцидента — `zone-b`, пресет `p-detour`; в `no_path` — `w-07`, `zone-c`, `p-no-path`.

| Состояние | Время | Что в кадрах | Правила |
|---|---|---|---|
| `initial` | идёт | как `normal` | `condition.close_working` своей выработки → `decision`; `run.start_preset` своего пресета → `preset_resetting` |
| `decision` | стоит | выработка `closed`, `closed_by = scenario`; условие в `conditions`; инцидент `active`, `trigger = passage_closed`; `run_state = paused`, `pause_reason = decision`; три варианта `offered` с общими `decision_id` (`d-0005-01`) и `comparison_key` и полным прогнозом. `detour`: у Р-03…Р-06 маршрут по съезду. `no_path`: у Р-07, Р-08 нет маршрута, у каждого варианта `forecast_no_route = 2`, `forecast_all_out = false`, `forecast_last_out_s` нет | `action.execute_option` с верным `decision_id` → `observe_exec`, `sw_exec` или `wa_exec`; с любым другим — `rejected`, `stale_decision`; `condition.open_working` → `decision_open` |

### `danger_zone`

### `reset`

`initial` — точка решения `detour` (пауза, условие `working_closed:w-12`). `run.reset` (цель любая, интерфейс шлёт `run`) → 202; две публикации `resetting` (состояние прежнее, `run_state = resetting`, подтверждения ещё нет); затем состояние `fresh`: `idSimulationRun = run-0006`, тик 0, исходное состояние рудника, `conditions` пуст, модель идёт. В `commands` нового прогона запись `{type: run.reset, run: run-0005, new_run: run-0006, status: applied}` с тиком старого прогона; `runs` пополняется `run-0005`, чей двойник имеет `completion_reason = reset` и не имеет `last_out_s`; журнал продолжается записями `run.reset` и `run.started`, `last_seq` не уменьшается. Повтор того же сброса с тем же `command_id` второго прогона не создаёт. В `fresh` правил нет.

## Чего здесь нет

- Никаких измерений стенда: ни задержек, ни размеров сообщений, ни поведения Ditto 3.3.7. Ответы составлены по проекту контракта.
- Сервер не проверяет то, что проверит только стенд: путь команды через live-сообщения и MQTT, запись в InfluxDB, заголовки авторизации.
- Запасные исходы вне правил не выводятся из модели: фикстура отвечает `not_scripted`.
